# Phase 4 仕様： 賭け対象の入口制限（A）とストーリーの導入

作成： 2026-11-13（Muse、企画・仕様担当）。決定の経緯は `PROJECT_PLAN.md`
の Phase 4 を参照。実装は Codex。着手前にリポジトリの `AGENTS.md` と
`docs/WORD_DICTIONARY.md` を読むこと。

## 1. 目的

- 賭けられる言葉を「重い言葉」に限定し、1回の取引での本文の変化量を
増やす。重い言葉は依存範囲が広いため、展開の変わるスピードが上がる
（ユーザーの狙い。進展性への対処も兼ねる）
- ストーリーに導入部を設け、主人公と状況をプレイヤー自身のものにして
から賭けを始める。導入がないと賭ける言葉が「ただの文字列」になり、
喪失の重さも着火（ニアミスによる熱）も弱まる

## 2. 仕様A： 賭け対象の入口制限

### 2.1 対象の定義（2026-11-13 ユーザー決定）

賭け対象は次のコマとする。判定はコマごとに行う。

- **含める**： 人物・場所・物・出来事を指す名詞的なコマ
- **含める**： 対象を特定する修飾（例： 「黄色い日傘」の「黄色い」。
黄色い単体も賭けられる）
- **含めない**： 程度・様態を表す副詞類、接続表現、形式名詞的な軽いコマ、
一般的な動作（現行で対象外のものはそのまま対象外を維持する）

動詞コマの扱い（2026-11-13 ユーザー承認）： 現行の線引きを維持する。
場面を担う「意味ある動詞のまとまり」は核に準じて対象とし、一般的な
動作は対象外とする。

### 2.2 判定方式

- 判定はルール側（形態素ルール＋ゲーム辞書）で行う。AI の採点・判定で
選択肢を塞がない（現行の不変条件）
- 実装は、既存の選択可否判定への追加フィルタとして設計する。区切り
（セグメンテーション）とオフセットは変更しない
- 辞書例外の追加が必要な場合は `docs/WORD_DICTIONARY.md` の追記手順に
従う（実例と対比例をテストに足し、開始文の再生成まで行う）

### 2.3 分割の維持

- 「黄色い日傘」は「黄色い」と「日傘」の別コマのまま（2026-11-13
ユーザー）。フレーズを1コマにまとめない

### 2.4 開始文100件

- フィルタ適用後の条件で区切りと可否を再生成する
（`scripts/precompute_starter_analysis.py`）
- 全100件について、賭け対象のコマが **3個以上** あることを検証し、
結果を報告する。満たさない開始文があれば、勝手に件数を減らさず、
対象が増えるよう本文を調整するか、差し替え案をユーザーに提示して
止まる

### 2.5 自作文

- 開始時に解析を回し、賭け対象のコマ数を数える。**3個未満なら開始
させない**（2026-11-13 ユーザー）
- 表示文面の案： 「文章が短すぎます。人物や物、様子を表す言葉を
足して、もう一度入力してください」
- 現行の20〜100文字という入力制約は維持する

### 2.6 プレイ中

- 賭けと喪失で対象が減っても、既存仕様（成立する報酬だけを表示し、
要求数を値引きしない）で継続する。新規の救済は入れない

### 2.7 表示

- 対象外のコマは赤線なしで表示する（現行の非選択表示と同じ）。UI の
変更はしない

### 2.8 テスト観点

- 「黄色い日傘」で「黄色い」「日傘」の両方が対象になること
- 副詞・接続表現・形式名詞が対象外のままであること
- 開始文100件すべてで対象が3個以上あること
- 自作文で対象2個以下の入力が開始不可になること
- 元本文の完全復元と start/end の一致（従来どおり）

### 2.9 研究上の注意

- 対象範囲は実験条件の一部になる。A/B 比較や現行版との比較では、
対象範囲の版をそろえて記録する

## 3. 仕様B： ストーリーの導入

導入の必須はユーザーの見立て（2026-11-13）。以下の形式は Muse の
提案をユーザーが承認し、確定とした（2026-11-13）。

### 3.1 提案する形式： 2層構造

- **導入部**（1〜2文）： 誰が・どこで・何をしているかという前提を
短く示す。**賭け対象にしない**。書き換えの対象にもしない
（物語の同一性を保つ土台）
- **本文**： 現行どおり。賭け対象は本文のコマだけ

### 3.2 出し方

- 開始文： 導入＋本文のセットで事前に用意し直す（100件）。開始画面
では導入を本文の上に続けて表示する
- 自作文： 導入は任意入力（空でも開始できる）。入力があれば賭け対象
外として本文の上に表示する。対象コマ数の判定（2.5）は本文だけで行う
- 生成への扱い： 導入は編集対象に含めないが、本文の整合を取るための
文脈としてプロンプトには渡す

### 3.3 採らない案

- 導入も賭け対象に含める案： 土台まで消えると物語の同一性が保てず、
喪失の観察が濁るため採らない
- 主人公や舞台を選択肢から選ぶ案： 面白いが今回の範囲外。将来候補
として記録だけする

### 3.4 確定事項と作り方

- 導入の長さは1〜2文。自作文の導入は任意入力で確定
- 開始文100件の導入は、既存の開始文に書き足す方式とする。下書きは
実装側（Codex）が作り、一覧でユーザーが確認できる形にしてから
取り込む

## 4. 進め方

1. 仕様A（2章）を先に実装する（2026-11-13 に全て確定）
2. 仕様B（3章）を続けて実装する（2026-11-13 ユーザー承認で確定）
3. ギャンブルの名称変更と報酬の多様化は本仕様の範囲外（別仕様で扱う）
